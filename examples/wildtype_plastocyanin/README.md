# WOOPS worked example: wildtype plastocyanin

**A complete, real-system walkthrough for the two maintained WOOPS extensions.** This folder ships an actual plastocyanin molecular-dynamics excerpt, the two WOOPS input files that were used to analyze it, and **unedited `.dat` results generated by the Fortran programs**. You can examine the output without compiling anything, or run the programs yourself and compare your results with the included outputs.

This is a **user example**, not the independent numerical validation suite. The separate `validation/` directory addresses numerical validation against independently calculated Python results. This example focuses on getting someone from a PSF/PDB/DCD to interpretable WOOPS output.

## A. Quick start (recommended)

Place this entire directory at `examples/wildtype_plastocyanin/` within the WOOPS repository, beside the existing `src/`, `tools/`, and (if present) `validation/` directories:

```text
WOOPS-extensions/
├── src/
│   ├── nanodomain/              # Fortran source; builds map.e
│   └── kirkwood/                # separate Fortran source; builds map.e
├── validation/                  # optional, separate independent checks
└── examples/
    └── wildtype_plastocyanin/  # place THIS directory here
        ├── README.md           # this guide
        ├── run_example.sh      # compile, run both branches, compare
        ├── MANIFEST.json       # input/actual-result provenance and hashes
        ├── SHA256SUMS
        ├── .gitignore
        ├── input/
        │   ├── wildtype.psf    # topology (34,709 atoms)
        │   ├── wildtype.pdb    # beta-tagged atom selection
        │   └── wildtype.dcd    # 10 real-system frames
        ├── runs/
        │   ├── nanodomain/WOOPS_input
        │   └── kirkwood/WOOPS_input
        ├── sample_output/     # ACTUAL original Fortran-generated data
        │   ├── nanodomain/p1p2.dat
        │   └── kirkwood/
        │       ├── kirkwood_interface.dat
        │       ├── kirkwood_interface_summary.dat
        │       ├── kirkwood_PRO16_7A.dat
        │       ├── kirkwood_PRO16_7A_summary.dat
        │       ├── kirkwood_PRO16_10A.dat
        │       └── kirkwood_PRO16_10A_summary.dat
        ├── scripts/
        │   ├── compare_results.py  # compare to saved Fortran output
        │   ├── inspect_results.py  # readable summary of the .dat files
        │   ├── make_vmd_maps.py    # turn P1/P2/P21 into viewing-only PDBs
        │   ├── view_map.tcl        # load maps in VMD
        │   └── plot_kirkwood.py    # optional plotting example
        └── figures/
            └── pro16_7A_kirkwood.png # example plot from real output
```

Prerequisites to run the Fortran codes: `make`, GNU Fortran with OpenMP support, Python 3 (standard library only for example utilities). From the **repository root**:

```bash
bash examples/wildtype_plastocyanin/run_example.sh
```

This compiles `src/nanodomain/map.e` and `src/kirkwood/map.e`, runs each against the supplied trajectory in its own working directory, and checks the newly generated outputs against the original Fortran results in `sample_output/`. A successful run ends with `OVERALL: PASS`. It does **not** overwrite `sample_output/`, modify the Fortran source, or invoke the independent Python reference calculation.

If you already compiled the executables, avoid rebuilding:

```bash
bash examples/wildtype_plastocyanin/run_example.sh --no-build
```

For a different number of OpenMP threads:

```bash
OMP_NUM_THREADS=8 bash examples/wildtype_plastocyanin/run_example.sh --no-build
```

The work directories `runs/nanodomain/` and `runs/kirkwood/` are where **new** output and `run.log` are produced. Their transient results are ignored by the included `.gitignore`. The original results are **always retained** in `sample_output/`.

## B. What is in the trajectory?

The input represents a real **wildtype plastocyanin (PDB 1YLB)** system in TIP3P water, including its copper atom.

| Property | Value |
|---|---:|
| Total PSF/DCD atoms | 34,709 |
| Nonwater solute atoms (`beta=1`), including copper | 1,436 |
| Protein heavy atoms counted by WOOPS | 734 |
| Protein hydrogens | 702 |
| Water molecules | 11,091 |
| Water atoms (`beta=2`) | 33,273 |
| Water atom order in topology | `OH2`, `H1`, `H2` |
| Frames in this example | 10 |
| Frame separation | approximately 10 ps |
| Periodic boundary conditions | orthorhombic minimum image |
| Original water model | TIP3P (`wattype=0`) |

**Important about the time interval:** the original user-supplied `last_100ps.dcd` had 500 frames with a 0.2 ps output interval. This small example contains source frames **0, 50, 100, ..., 450** (zero-based) with *every original atom retained*. The **first-to-last sampled span is 90 ps**; the data comprise ten discrete configurations, **not 100 ps of contiguous frames and not ten consecutive frames**. These 10 snapshots are for learning the input/output interface and reproducibility, not for precise thermodynamic or kinetic estimates. The 199 MiB, 500-frame trajectory is deliberately not included in the repository.

`input/wildtype.psf` is the original topology (atom order and bonds preserved); `input/wildtype.pdb` retains that order and was prepared with `beta=1` on solute atoms including Cu and `beta=2` on waters. The PDB coordinates are for initial structure bookkeeping; WOOPS reads per-frame coordinates from the DCD. The trajectories retain periodic boxes. Do not reorder atoms in just one of these files: **PSF, PDB, and DCD must agree exactly in atom ordering**.

### Check files before running

From this example directory:

```bash
sha256sum -c SHA256SUMS
```

macOS alternative: `shasum -a 256 -c SHA256SUMS`. The checksums cover the three inputs and seven original Fortran output files. They will not change when you rerun WOOPS.

## C. The two executables are different programs

The maintained repository contains two separate Fortran variants sharing a common reader and many geometric conventions:

| | `src/nanodomain` | `src/kirkwood` |
|---|---|---|
| Main question | How are hydration waters oriented around each protein atom? | How are water dipoles collectively correlated in selected shells? |
| Scope | All water oxygens within 7 Å of any solute atom, assigned to nearest solute **heavy** atom | All-interface 7 Å, PRO16 carbonyl O–centered 7 Å, and PRO16 carbonyl O–centered 10 Å |
| Output | One averaged `P1/P2/P21` row per solute atom | Per-frame `g_K`, `g_perp`, `g_parallel`, occupancy and diagnostics, plus summary |
| Number of outputs | One `p1p2.dat` | Six `kirkwood_*.dat` files |
| Parallelization | OpenMP | OpenMP |

You must compile and run each source branch separately. A single `map.e` does **not** offer a switch between the two calculations.

## D. Manual run (to understand the input format)

The wrapper above is optional. These are the actual shell commands from the repository root:

```bash
make -C src/nanodomain
make -C src/kirkwood

# Paths in WOOPS_input are relative to the current working directory.
(cd examples/wildtype_plastocyanin/runs/nanodomain && \
    ../../../../src/nanodomain/map.e < WOOPS_input > run.log 2>&1)

(cd examples/wildtype_plastocyanin/runs/kirkwood && \
    ../../../../src/kirkwood/map.e < WOOPS_input > run.log 2>&1)

python3 examples/wildtype_plastocyanin/scripts/compare_results.py
```

Each `runs/*/WOOPS_input` has **the same eleven lines**:

```text
../../input/wildtype.psf
../../input/wildtype.pdb
../../input/wildtype.dcd
restart
100
1436
0
10
1
10
1
```

The lines mean:

| Line | What it controls | Example value | Notes |
|---|---|---|---|
| 1 | PSF filename | `../../input/wildtype.psf` | Resolved relative to `runs/<branch>/`, **not** the repository root |
| 2 | PDB filename | `../../input/wildtype.pdb` | Must contain `beta=1`/`beta=2` selection flags |
| 3 | DCD filename | `../../input/wildtype.dcd` | Same atom ordering as PSF/PDB |
| 4 | Restart basename | `restart` | Restart/leg file written to the run directory |
| 5 | Solute-residue count (legacy control) | `100` | Includes residue 100, copper, in this system |
| 6 | Number of solute atoms | `1436` | Must agree with `beta=1` count |
| 7 | Water model | `0` | `0` TIP3P; `2` SPC/E; `1` TIP4P unsupported |
| 8 | Total frames requested | `10` | This run uses all 10 frames |
| 9 | First analyzed frame | `1` | One-based |
| 10 | Final analyzed frame | `10` | One-based |
| 11 | Restart/leg-control flag | `1` | Required value for the maintained Kirkwood implementation |

`WOOPS_input` has **no named keys**; the Fortran reader reads values in order. Do not insert comments or extra lines. If you replace the data with your own simulation, update the paths, solute counts, water model, and frame range. **Run the executable from the directory where those relative paths are correct.**

To confirm execution:

```bash
# From the repository root
less examples/wildtype_plastocyanin/runs/nanodomain/run.log
less examples/wildtype_plastocyanin/runs/kirkwood/run.log
```

Successful logs end with `COMPLETED SUCCESSFULLY`. The Kirkwood log also prints its internal geometry/sum sanity checks and three summary regions. All frame-level output is written into the current working directory, not alongside the executable.

## E. Reading `p1p2.dat` (nanodomain)

Actual first output row, from **`sample_output/nanodomain/p1p2.dat`**:

```text
DATA DI :         10    1   1         N         VAL          -0.3000000000    0.6482569071    0.3115786082   -0.0840197038
```

There are **1,436 such rows**, one for every `beta=1` solute atom (including Cu). Each row contains:

```text
DATA DI :  n_frames  atom_id  residue_id  atom_name  residue_name  q  P1  P2  P21
```

In this row, atom 1 (`N`, VAL1, partial charge −0.3 e) has 10-frame mean `P1=0.6482569071`, `P2=0.3115786082`, and `P21=−0.0840197038`. These are dimensionless. For each selected water, the local normal `n` points from its nearest solute heavy atom toward the water oxygen, and `u` is the unit water dipole. Then

$$
P_1 = \mathbf{u}\cdot\mathbf{n},\qquad
P_2 = \frac{3(\mathbf{u}\cdot\mathbf{n})^2-1}{2}.
$$

The third parameter, $P_{21}$, also characterizes orientation of the water molecular plane (see `src/nanodomain/README.md` for the exact angular convention).

**How the averaging works:** in every frame, selected waters are assigned to the *nearest protein heavy atom*; their order parameters are averaged **within that frame** for that heavy atom. Each frame then contributes exactly once to the trajectory average. Bonded solute hydrogens inherit their parent heavy atom's values. A heavy atom without any assigned waters in a frame contributes **zero** in that frame, rather than being removed from the denominator. Thus a zero in `p1p2.dat` is **not** automatically evidence of isotropic water; it may indicate no assigned hydration waters across the sample. For this short example, many atoms have zeros.

Averages over these ten sampled frames are illustrative only: they are not a well-converged wildtype hydration map.

## F. Reading Kirkwood time series and summaries

`sample_output/kirkwood/` contains **six actual WOOPS output files**:

- `kirkwood_interface.dat` and `kirkwood_interface_summary.dat`: water oxygen within 7 Å of **any** solute atom, including hydrogens.
- `kirkwood_PRO16_7A.dat` and `kirkwood_PRO16_7A_summary.dat`: oxygen within 7 Å of the PRO16 backbone carbonyl oxygen.
- `kirkwood_PRO16_10A.dat` and `kirkwood_PRO16_10A_summary.dat`: oxygen within 10 Å of that same oxygen.

The PRO16 regions use the carbonyl O for **membership selection only**; the `n_i` vector for each water still points from its nearest protein heavy atom toward its oxygen. For a selected water with unit dipole $\mathbf u_i$, define $p_i=\mathbf u_i\cdot\mathbf n_i$ and $\mathbf u_{i,\parallel}=\mathbf u_i-p_i\mathbf n_i$. The production code uses the *instantaneous occupancy* $N(t)$ and evaluates

$$
 g_K(t)=\frac{|\sum_i\mathbf u_i|^2}{N(t)},\qquad
 g_\perp(t)=\frac{(\sum_i p_i)^2}{N(t)},\qquad
 g_\parallel(t)=\frac{|\sum_i\mathbf u_{i,\parallel}|^2}{N(t)}.
$$

The `.dat` time-series files are **CSV**, even though their extension is `.dat`. Each has this header:

```csv
frame,valid,N,normal_coherence,g_k,g_perp,g_parallel,decomposition_residual
```

`valid=1` means one or more waters are in the region. When `N=0`, `valid=0`; those frames are kept in time series but omitted from summary averages. `normal_coherence=|Σ_i n_i|/N` measures alignment of the different local surface-normal vectors. The `decomposition_residual` column is `g_k - g_perp - g_parallel`.

**Do not assume** `g_K = g_perp + g_parallel` for a curved interface: the normals differ from water to water, and cross terms survive. The full interface in this example has large nonzero residuals; this is **not** itself a numerical failure. Likewise, the common-normal isotropic ratios 1/3 and 2/3 are benchmarks, not constraints on this fluctuating, locally defined interface.

The `_summary.dat` files contain comment lines describing their 15 columns, followed by one numeric row. This is what WOOPS actually produced for these ten snapshots:

| Region | Mean occupancy $\langle N\rangle$ | $\langle g_K\rangle$ | $\langle g_\perp\rangle$ | $\langle g_\parallel\rangle$ | Mean residual |
|---|---:|---:|---:|---:|---:|
| Full interface, 7 Å | 1108.80 | 1.717240 | 11.771607 | 1.220843 | −11.275210 |
| PRO16, 7 Å | 9.70 | 1.537279 | 0.604536 | 0.914062 | +0.018681 |
| PRO16, 10 Å | 45.10 | 1.059021 | 1.041393 | 0.919932 | −0.902304 |

These are **short illustrative sample averages**, not statistically converged estimates. In all three regions, all 10 retained frames are valid (nonzero occupancy).

For a compact textual report using the shipped results (Python standard library only):

```bash
python3 examples/wildtype_plastocyanin/scripts/inspect_results.py
```

To inspect your newly generated data instead:

```bash
python3 examples/wildtype_plastocyanin/scripts/inspect_results.py --results runs
```

## G. Using the results: VMD example maps

The map data are numeric tables, **not** colored molecular structures. A quick way to visualize the three map fields is to create three **view-only** PDBs that store each WOOPS value in the PDB temperature-factor (`Beta`) column. This uses only Python's standard library:

```bash
# From repo root; defaults to original Fortran data in sample_output/
python3 examples/wildtype_plastocyanin/scripts/make_vmd_maps.py

# Optional: use the outputs you just generated instead
python3 examples/wildtype_plastocyanin/scripts/make_vmd_maps.py --results runs
```

This creates `derived/p1_map.pdb`, `derived/p2_map.pdb`, and `derived/p21_map.pdb`. With VMD installed, run (from the example directory):

```bash
vmd -e scripts/view_map.tcl
WOOPS_MAP=p2 vmd -e scripts/view_map.tcl
WOOPS_MAP=p21 vmd -e scripts/view_map.tcl
```

The VMD script loads the original PSF with the derived PDB to recover connectivity and colors solute atoms by `Beta`; the example representation is a simple licorice view. This is an introductory visualization, **not** the production publication renderer used for plastocyanin figures. You can change the representation and color scale interactively in VMD.

**Crucial:** the PDB `Beta` field originally held the WOOPS **solute/water selection flags** (1 and 2). The viewing-only PDBs overwrite that field with order parameters, so **never reuse `derived/*_map.pdb` as input to WOOPS**. Keep using `input/wildtype.pdb` for the actual calculation.

A simple figure made from the original `kirkwood_PRO16_7A.dat` is included at `figures/pro16_7A_kirkwood.png`. You can regenerate it (requires optional `matplotlib`):

```bash
python3 -m pip install matplotlib
python3 examples/wildtype_plastocyanin/scripts/plot_kirkwood.py --region PRO16_7A
```

It is a demonstration of the time-series output, not an equilibrium analysis.

## H. Compare your rerun against the original WOOPS results

Without rerunning (to inspect the baseline):

```bash
python3 examples/wildtype_plastocyanin/scripts/inspect_results.py --results sample_output
```

After running the Fortran programs:

```bash
python3 examples/wildtype_plastocyanin/scripts/compare_results.py
```

The comparison script has **no external dependencies** and verifies:

1. All 1,436 nanodomain `DATA DI` records, including atom IDs, names, residue metadata, charges, and `P1/P2/P21`.
2. Frame numbers, occupancy, validity flags, and all floating-point fields for each of the three ten-frame Kirkwood series.
3. The 15 numeric summary fields for each Kirkwood region.

Floating-point comparisons default to `atol=2e-9`, `rtol=1e-9` to tolerate small arithmetic differences across computers and thread counts. Errors, missing records, malformed files, or nonfinite values trigger a nonzero exit code. `sample_output/` is never rewritten. The comparison is a **reproduction check against the original WOOPS program**, not proof of scientific correctness; see `validation/` for the independent Python cross-check.

## I. Troubleshooting and adapting to your own systems

**Can't find the PSF/PDB/DCD?** The first three control-file paths are relative to the `runs/nanodomain` or `runs/kirkwood` working directory. Run from that directory, or use `run_example.sh`. If you move the input files, edit all three paths.

**Incorrect atom counts or unsupported water type?** PSF and PDB atom order must correspond to the DCD, and all selected waters must be three-site O,H,H molecules. The beta-tagged PDB must use 1 for solute and 2 for water. The example uses TIP3P (`0`) and an orthorhombic periodic cell. TIP4P (`1`) is not supported by these maintained programs.

**Compile errors?** Use `gfortran` with `-fopenmp` and `make`. See the makefiles in `src/nanodomain` and `src/kirkwood`; `make clean && make` from each branch is a safe full rebuild.

**Results appear in the wrong directory?** The program writes into its **current working directory**. Feeding an input file via `< path/to/WOOPS_input` while running from elsewhere doesn't change the working directory.

**Output differs slightly between runs?** Small floating-point differences may arise from compiler optimization and OpenMP reduction ordering. Use the numerical comparator rather than a byte-for-byte `diff`. Large differences warrant examining the PDB beta flags, box, frame range, Fortran version, and whether you compiled the intended source branch.

**The nanodomain map has many zeros.** Zero means zero accumulated contribution under this normalization; it is not a test of true isotropy. A small ten-frame sample cannot populate every atom equally.

**Kirkwood perpendicular and parallel factors don't sum to `g_K`.** They needn't for different water-specific normals. Inspect the residual and coherence columns instead of imposing the common-normal identity.

**Longer production runs.** Increase the frame request and point to your production trajectory. Analyze independent DCD legs separately where appropriate; see `tools/nanodomain/process_woops_legs.py` and `tools/kirkwood/process_kirkwood_timeseries.py` for aggregation of complete simulation output. Do not treat these ten-example snapshots as publishable 100 ps averages or reliable time-correlation data.

## J. Provenance and scope

The example is based on the **user-provided wildtype 1YLB plastocyanin PSF and 100 ps DCD**. Only a temporal subset was retained to keep it small; no atoms were removed. The seven `sample_output/` files are copied directly from a successfully completed run of the two maintained WOOPS Fortran executables on these ten frames. `MANIFEST.json` and `SHA256SUMS` record checksums of the supplied inputs and original results. The example generator and comparison do not edit Fortran physics.

For formulas and implementation details, consult `src/nanodomain/README.md` and `src/kirkwood/README.md`. For a calculation **independent of the Fortran program**, see the repository's separate `validation/` suite.
